# 乐谱分享方案（SCORE）：曲库、版权口径、内容维护、展示层

> 目标：在 `https://ijipu.pages.dev` 上加一个「乐谱」区。每份谱都能**看源码、看效果、进应用编辑**；
> 列表能按标题/封面浏览；从抖音、小红书过来的链接打开就能看；以后**只加文件、不改代码**就能维护。
>
> 本文是**方案**，不是已完成的工作。第七节列出必须由你拍板的点。

---

## 零、结论速览

| 你问的 | 建议 | 一句话理由 |
|---|---|---|
| 1 版权 | 只做「公版 / 原创 / 授权」三类；在版权期的整首不放；片段按第二十四条第二项严格限量 | 脚本只是载体，音乐作品本身仍受保护；公版是唯一长期干净的路 |
| 2 上传方式 | **Git 当 CMS**：`public/scores/<slug>/` 放 `score.jps` + `meta.json`，构建时生成页面与索引 | 站点是纯静态；加/改/删 = 改文件；有历史、能回滚、能审 |
| 2 账号 | 现在**不做**；以后要投稿，走「Issue 表单 → Worker + Cloudflare Access」，仍不自建密码体系 | 账号 = 数据库 + 找回密码 + 滥用处理，和"轻"的定位不符 |
| 3 水印/背景 | 分三层：谱面层（随谱）/ 站点展示层（不写进谱）/ 分享卡（构建期出图） | 混在一起会污染 `.jps`，也会让"复制给别人效果一致"失效 |
| 4 实例页 | `/scores/<slug>/`：源码 + 预览 + 在应用里编辑 + 下载/复制；短链 `/s/<id>` | 分享场景要"打开就能看、想改就能改" |
| 5 列表 | `/scores/`：静态卡片（封面 + 标题 + 作者 + 标签 + 许可证 + 难度），JS 只负责筛选 | 列表要能被搜索/分享，卡片要能一眼认出是哪首 |

> **已拍板（2026-11-03）**
> 1. 曲库只放**公版 + 原创/授权**（A + B），不做 C/D。
> 2. 起步就用**现有示例**：7 首曲子 / 8 个条目（详见 2.5）。
> 3. **首页示例与曲库合一份**：`public/scores/` 是站点唯一真源；首页从它 `?raw` 导入，不再在 TS 里手写第二份。
> 4. **短链做**：`/s/<短码>` 301 到详情页，P0 就有。
> 5. **站点水印用 A**：页面角标 + 分享卡完整标识；斜向重复作为将来可选。
> 6. **内容许可证用 CC BY-NC-SA 4.0**（记谱/排版），页面加「商用请联系」；**不单独加"旋律：公版"那一行**。
> 7. 投诉渠道：**`+copyright` 别名发不出去**，改用主地址 `snail.zh@foxmail.com` + 主题前缀 `【版权投诉】`（见 10.4）。

## 二、版权（问题 1）

> 以下是工程判断和操作口径，**不是法律意见**。真遇到纠纷要找律师。

### 2.1 先把直觉纠正过来

1. **「只分享脚本、不传音频和 PDF」不等于避开版权。** 乐谱是音乐作品的表现形式（《著作权法》第三条第三项）；
   把旋律记成 `.jps` 属于复制（第十条第五项），放到网上属于信息网络传播（第十条第十二项）。
   载体是文本还是图片，不影响定性。
2. **保护期**：自然人作品 = 作者终生 + 死后 50 年，截止第 50 年的 12 月 31 日（第二十三条）。
   **2026 年，作者 1975 年及以前去世 → 已公版；1976 年以后去世 → 还在保护期。**
3. **歌词是另一件作品**（文字作品）。曲公版，不代表词也公版（老曲配现代填词的情况很常见）。
4. **编配/整理/翻译有独立权利**（第十三条）。曲公版，**不等于"别人整理的那一版"公版**；
   也不要整份抄别人写的 `.jps`——那份具体记谱也可能有整理者的劳动。
5. **「只取几小节」不自动安全**。第二十四条第二项要求"为介绍、评论或说明问题，适当引用"，
   还要"不影响正常使用、不损害权利人利益、署名"。而音乐的记忆点可能只有 2 小节
   （`src/landing/samples.ts` 第 15-16 行已经写过这句话）。
6. **全球访问的差异**：中国是死后 50 年，欧美多为 70 年。站是全球可访问的，**按更保守的选**
   （†70，或 1929 年前出版）最稳；做不到就至少留余量（比如 †60）。

### 2.2 别的乐谱网站怎么处理

- **MuseScore**：有明确的版权投诉通道和 DMCA agent（[官方说明](https://help.musescore.com/en/articles/8535925-submit-a-copyright-takedown-request)），
  收到权利人通知就下架；另有与版权方合作的官方曲谱区。它的模型是「用户上传 + 投诉下架 + 授权合作」。
- **国内简谱站**：多数也是「用户上传 + 投诉下架」。这不代表合法，只代表**风险被推到收到投诉之后**。
- **你和它们的关键区别**：你现在是**自己策展**（不是开放上传）。自己策展 = 你是直接行为人，
  "通知—删除"那条避风港保护不了"我自己挑的侵权内容"。所以策展标准必须自己守住。
  这反而是好事：内容可控、质量可控。

### 2.3 建议的内容分级

| 级别 | 判据 | 整首放？ | 可下载？ | 页面标识 |
|---|---|---|---|---|
| **A 公版** | 作者 †≤1975；传统民歌且无现代编配；匿名作品发表满 50 年 | ✓ | ✓ | 「公版」 |
| **B 原创/授权** | 你自己写的/编的；有书面授权；CC 授权 | ✓ | ✓（按授权） | 「原创」/「已授权」 |
| **C 教学片段** | 在版权期；≤8 小节；为了讲某个语法点；附来源与购买/收听链接 | 片段 | ✗ | 「片段 · 教学用」 |
| **D 整首流行歌** | 在版权期 | ✗ | ✗ | 不做 |

> 起步阶段建议**只做 A + B**。C 也先别碰：等站子有稳定受众、真的收到过一次投诉、知道流程怎么走，再考虑。

### 2.4 站点要有的东西（操作层）

1. 每份谱的 `meta.json` 必填 `license` 与 `source`（来源/版本说明），页面显示徽标。
2. 单独一页 `/copyright/`：投诉邮箱（沿用 `snail.zh@foxmail.com`）、需要提供的信息、
   处理时限（**收到后 48 小时内先下架、再核实**）、下架记录。
3. 若开放投稿：投稿页一句声明——"你保证有权授权；侵权责任由投稿人承担；本站可无理由下架"。
4. 第一阶段**不做付费下载、不做广告分成**；赞赏只对工具，不对谱。
5. 留证据：收到投诉的时间、内容、处理动作存一份（邮件/截图）。
6. 代码是 AGPL-3.0，**乐谱内容不是**。要在页脚/版权页写清两套许可，避免别人误以为谱也是 AGPL。

## 三、内容怎么加/改/删（问题 2）

### 3.1 三个方案对比

| 维度 | A. Git 当 CMS（推荐） | B. Cloudflare R2 直传 | C. 账号系统 |
|---|---|---|---|
| 新增一份谱 | 加 2 个文件，push，自动构建 | 上传对象 + 自己写清单 | 登录 → 表单 → 数据库 |
| 审核 | 提交记录，天然可审 | 无 | 要自己做 |
| 版本/回滚 | git 历史，一键回滚 | 对象版本（要开） | 自己实现 |
| 删除 | 改状态留下架页；或删文件 | 删对象，索引要同步 | 软删除 + 权限 |
| 搜索/索引 | 构建时生成 | 自己维护 | 数据库 |
| 安全面 | 只有仓库写权限 | 上传接口 + token | 密码/会话/CSRF/找回 |
| 适合规模 | 几十到几百份，1-3 人维护 | 大量二进制 | 开放 UGC |
| 维护成本 | 几乎为零 | 中 | 高 |

**结论：A。** 站点现在是静态的；上 B/C 等于先造一个后台，再用它维护几十份谱，不划算。

### 3.2 目录与元数据

```
ijipu/public/scores/            ← 站点唯一真源（首页示例也读这里）
  index.json                    ← 构建时生成（列表页读取）
  xiao-xing-xing/
    score.jps                   ← 谱面本体
    meta.json                   ← 站点元数据（不进 .jps）
    assets/cover.webp           ← 可选：作者提供的封面
    assets/bg.webp              ← 可选：谱面背景/水印图
  mo-li-hua/
    meta.json                   ← file: "/samples/茉莉花.jps"（引用，不复制）
  song-bie/
    meta.json                   ← file: "/samples/送别.jps"（完整版，引用）
  song-bie-dsb/
    score.jps                   ← 首页那 4 小节 {dsb} 演示（新建条目）

ijipu/public/samples/           ← 应用「打开示例」用的 2 首，保持不动
  茉莉花.jps
  送别.jps
```

**为什么元数据放外面**：`.jps` 要保持"纯谱"，能被应用、插件、别人原样打开；
站点字段（slug、标签、上架时间、下架原因）写进去就污染了，也违背"谱面自包含"。
这和应用里 L1/L2 分层是同一条线。

**为什么允许 `file` 引用**：《茉莉花》《送别》已经有一份原文在 `public/samples/`（应用在用），
曲库再复制一份就会两头维护。`meta.file` 只是"指过去"，正文仍只有一份。

`meta.json` 字段（草案）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `slug` | ✓ | URL 段，小写字母/数字/连字符；必须与目录名一致 |
| `title` / `composer` | ✓ | 曲名、作曲/作词；公版写「传统」 |
| `license` | ✓ | `PD` / `ORIGINAL` / `AUTHORIZED` / `CC-BY-4.0` / `CC-BY-NC-SA-4.0` / `EXCERPT` |
| `source` | ✓ | 来源说明或链接（公版写卒年；授权写授权方） |
| `file` | | 引用已有 `.jps`（相对 `public/`，如 `/samples/茉莉花.jps`）；省略则用本目录 `score.jps` |
| `tags` / `difficulty` | | 语法点标签（「多声部」「跳房子」「倚音」）、难度 1-5 |
| `excerpt` | | 是否片段（`EXCERPT` 时必填小节范围） |
| `status` | | `published` / `retired`；`retired` 出下架页，不 404 |
| `retiredReason` / `retiredAt` | | 下架原因与时间（`retired` 时必填） |
| `short` | ✓ | 可念的自定义短码（3-6 位小写字母，如 `mlh`、`songb`；不用随机码），发布后不改 |
| `cover` | | `assets/cover.webp` 或省略（省略 = 自动用首页谱面做封面） |
| `card` | | 页面皮肤：`paper` / `ink` / `brand` / `minimal`（见第 5 节） |
| `watermark` | | 站点水印：`corner`（默认）/ `tile` / `none`（见 10.2） |
| `note` | | 编配说明（Markdown，复用 `src/help/markdown.ts`） |
| `publishedAt` / `updatedAt` | ✓ | 上架/更新时间（`YYYY-MM-DD`） |

### 3.3 三种操作

| 操作 | 怎么做 | 结果 |
|---|---|---|
| **新增** | 建目录 → 放 `score.jps` + `meta.json` → 本地 `npm run build` 看效果 → commit/push | Pages 自动构建（1-2 分钟） |
| **更新** | 改 `score.jps`，改 `updatedAt` | 页面显示「更新于」 |
| **下架** | `status` 改 `retired`，写原因/时间 | 链接仍能打开，显示「已下架 + 原因 + 联系」 |
| **改 slug** | `public/_redirects` 加 `301 /scores/old /scores/new` | 旧链接不 404；短链不变 |

**不要直接删目录**：分享出去的链接会 404。下架页比 404 有信息量，也避免"内容被删了"的误会。

**手机上怎么改**：GitHub 网页版能改小文件；大改用 `github.dev`（在仓库页按 `.` 打开 VS Code 网页版）。
不需要装工具链。**页面上不提供上传按钮**——现在的"上传"就是"把文件放进 `public/scores/` 并提交"。

### 3.4 构建时要拦的错（闸门）

新增 `scripts/gen-scores.mts`（构建期跑，详细接法见 4.6）：

1. `meta.json` 字段齐全、枚举合法、**未知字段报错**（防手滑）。
2. `slug` 合法、不重复、与目录名一致。
3. 每份 `.jps` 用引擎解析：**错误 = 构建失败**；**告警默认也失败**（站点不发布带告警的谱），确有需要走白名单并写明理由。
4. `assets` 里每个文件存在、扩展名在白名单、单文件 ≤300KB、长边 ≤2000px（构建只检查，不转码）。
5. `short` 唯一（**含已下架 `retired`**）、只含 `a-z`、长度 3-6、不在保留字表；已下架的码不复用。
5. 输出确定性：`index.json` 按 slug 排序；同一输入两次构建字节一致。
6. `sitemap.xml` 覆盖所有 `published` 的详情页；`/s/<short>` 都能 301 到存在的详情页。
7. 列表页在没有任何谱时也要能打开（空状态 + 一句"正在收录"）。

### 3.5 以后要开放投稿（升级阶梯，仍然不建账号）

| 级别 | 做什么 | 触发条件 |
|---|---|---|
| 2 | GitHub Issue 表单（曲名/作者/授权/来源/附件）+ PR 模板，维护者合并 | 偶尔有人投稿 |

**明确不做**：把 PAT 放前端、自建密码体系、手动传 `dist`（会和 git 源漂移）。

## 四、列表与详情页（问题 4、5）

### 4.1 URL 设计

| URL | 用途 | 说明 |
|---|---|---|
| `/scores/` | 列表：卡片、筛选、搜索 | 静态 HTML 里就有全部卡片，JS 只做筛选 |
| `/scores/<slug>/` | 详情：源码 + 预览 + 操作 | **规范链接**，进 sitemap |
| `/s/<short>/` | 短链，301 到详情 | 二维码、口播、字幕用 |
| `/app/?src=<编码后的 .jps 地址>` | 在应用里打开并编辑 | **新增**；图片基准要等 P2 的 URL 通道 |
| `/app/?jps=<源码>` | 已有，只适合短谱 | 8000 字符上限 |

短链为什么要：二维码码点少一半、口播好念、平台里被折叠也不怕。

卡片要有的信息：**封面、标题、作曲/作词、语法点标签（≤3）、许可证徽标、难度、更新日期**。
排序默认：`featured` 先，再按 `publishedAt` 倒序。

**封面怎么来**（回答"标题图片"）：

1. **默认自动**：构建期用引擎渲染第一页、裁到墨迹，输出 `cover.svg`，当 `<img>` 用。

4. 卡片比例 16:10，`object-fit: contain`（**谱面不能裁**，裁了会缺音符），底色用页面皮肤。

> 列表页**不在构建期用无头 Chrome 截图**：CI 里有没有 Chrome 我没验证，不该把构建依赖押在它身上。
> 需要 PNG（og 卡、微信转发）的，放本地脚本生成、提交进仓库——和 `public/site/*.webp` 一样。

- 桌面：左右两栏（和应用的拆分视图同构）；手机：上预览、下源码（可折叠/标签切换）。
- 「脚本 / 预览」的 DOM 与样式**直接复用 `src/help/jpsPreview.ts`**，不另写一套。

  这样抖音/小红书的内置浏览器也能秒开。
- 操作按钮：**在网站里编辑**（→ `/app/?src=…`，同窗口跳转）、下载 `.jps`、下载 `.zip`（谱 + 图，构建期打好）、复制源码。
- 页尾：`license` + `source` 原文、投诉入口、上下架时间。

### 4.4 抖音/小红书：按"最坏情况"设计

| 限制 | 后果 | 应对 |
|---|---|---|
| 不能装 PWA、Service Worker 常不可用 | 离线/二次打开慢 | 页面本身轻；**不承诺离线** |
| `<a download>` 常被拦 | 下载按钮点了没反应 | 点完提示"已复制/请长按源码复制"，别只靠下载 |
| `navigator.clipboard` 可能被拒 | 复制失败 | 退回 `textarea.select()` + `execCommand`，再不行提示长按 |
| `window.open` 可能被拦 | 新窗口打不开 | 一律同窗口 `location.href` |
| 竖屏、可点区域小 | 谱面看不清 | 移动优先；预览可横向滚动、有「满宽」模式 |
| 笔记正文里的外链不可点 | 平台里点不到链接 | 视频/图文里用**二维码**或主页固定链接；页面给「复制链接」 |
| 没有系统字体 | 谱面字体回退 | 引擎已用系统字体栈，不依赖下载字体 |

建议加一条 UA 提示：抖音（`aweme`）/小红书（`xhs`/`discover`）里打开时，
顶部一行小字「建议在浏览器中打开，编辑与下载更完整」，**不挡内容**。

> 平台侧的现实：多数普通账号的笔记/视频正文不能挂可点击外链（企业号/组件另说），
> 所以**二维码 + 主页固定链接 + 口播短链**是主路径，别把转化全押在"点链接"上。

### 4.5 「编辑」的边界

- `/app/?src=` 打开的是**导入副本**：不绑原文件、标记为已修改，保存走"下载 / 复制"，
  **不会回写站点**。别人改你的谱，也影响不到你的原件。
- 需要"保存回网站"就是投稿流程（3.5），不是编辑器直接写仓库。
- 试听、动态谱视频、对拍仍归应用/桌面，网站不放这些入口（1.4 的分类）。

### 4.6 怎么生成（技术接法）

站点是静态多页，详情页有两种做法：

| 做法 | 优点 | 缺点 |
|---|---|---|
| A. 客户端渲染（一个 `/scores/view/?id=`） | 简单 | 分享卡/SEO 差；内置浏览器里白屏等 JS |
| **B. 构建期生成静态 HTML**（推荐） | 首屏快、可索引、og 完整 | 要先加一个构建步骤 |

B 的具体做法（不引新框架）：

1. 新增 `scripts/gen-scores.mts` + `vite.scores.config.ts`（照 `vite.smoke.config.ts` 的 lib 打包套路：
   `vite build --config vite.scores.config.ts && node dist-scores/gen-scores.cjs`），
   这样脚本能 import `@ijipu/engine`、`src/brand/tokens.ts`、`src/brand/siteBoot.ts`、`src/help/markdown.ts`。
   ⚠ 只 import 纯常量与纯函数，别调这些模块里的 DOM 函数。
2. 构建顺序：`npm run build` 里在 `vite build` 之后加 `npm run scores:gen`；
   Cloudflare Pages 的构建命令仍是 `npm run build`，不用改面板配置。
   目录为空时脚本直接跳过（不影响现在的构建时长）。
3. 生成物（全部落在 `dist/`，不写回 `public/`）：
   - `dist/scores/index.html`（列表）
   - `dist/scores/<slug>/index.html`（详情，SVG 内联）
   - `dist/scores/<slug>/cover.svg`（自动封面）
   - `dist/scores/index.json`（筛选/应用读取）
   - `dist/sitemap.xml`、`dist/_redirects`（短链，追加到 `public/_redirects` 的内容后面）
4. `public/scores/**` 里的 `score.jps`、`meta.json`、`assets/*` 会被 Vite 原样复制到 `dist`，
   正好充当"下载源码/图片"的真实文件，不用再拷一遍。
   样式放 `public/scores/scores.css`（稳定路径、不带 hash），生成的页面直接 `<link>` 它；
   色值仍从 `src/brand/tokens.ts` 注入，不在 CSS 里另抄一套。
5. **开发时**：详情页只在 `dist` 里存在，所以本地要 `npm run build && npm run verify:site` 看效果
   （和现在验官网的方式一致）；`npm run dev` 仍然只跑应用。

> 备选：写一个 Vite 插件在 dev 里也生成同样的页面。能省一次 build，但多约 150 行插件代码，
> P0 不做，等真的天天改曲库时再说。

### 4.7 要同步改的现有位置（漏一个就坏）

| 位置 | 改什么 | 不改会怎样 |
|---|---|---|
| `package.json` | `build` 末尾加 `npm run scores:gen`；新增 `scores:gen` / `score:cover` | 部署后曲库不更新 |
| `public/sw.js` | `fallbackFor` 加 `/scores/` 与详情页；未命中时回列表 | 离线打开曲库白屏 |
| `public/_redirects` | 短链 301；构建时追加到 `dist/_redirects` | 短链 404 |
| `src/landing/*` 与各页顶栏 | 「乐谱」入口（首页/文档页顶栏） | 用户找不到 |
| `vite.config.ts` | **不用加**（详情页由脚本生成，不是 Vite 入口） | ——（这里特意选"不加"，避免动 7 入口的构建） |
| `src/landing/samples.ts` | 6 段手写源码改成从 `public/scores/*/score.jps` `?raw` 导入（"合一份"） | 首页和曲库各维护一份，早晚不一致 |
| `scripts/smoke.mts` | 8.1 的断言 + 十几处 `public/samples` 路径（"合一份"后要跟着改） | 内容漂移没人发现；断言指向旧路径 |
| `scripts/verify-site.mjs` | 8.2 的检查 | 真浏览器里坏掉没人发现 |
| `public/404.html` | 兜底页（P0，手写） | 死链不好看 |
| `dist/sitemap.xml` | 由生成器写（覆盖静态页 + 曲库） | 漏收录 |

> `vite.config.ts` 不用改是这次设计的一个好处：详情页是构建期生成的静态 HTML，
> 不占 Vite 入口，也就不碰"7 个入口 + 桌面壳 + 嵌入版"那串暗耦合。

## 五、水印 / 背景 / 卡片（问题 3）

### 5.1 先分三层，不要混

| 层 | 写在哪 | 谁看得见 | 用途 |
|---|---|---|---|
| **谱面层（L2）** | `.jps` 的 `# jps-config`（`wm*` / `bg*`） | 应用、插件、桌面、网站，**跟着文件走** | 作者自己要的水印/背景 |
| **站点展示层** | 页面 HTML/CSS + `meta.card` | 只在网站 | 纸面/卡片框、站点角标、许可证徽标 |
| **分享卡** | 构建期/本地生成的 `og.png` | 转发预览 | 品牌与二维码 |

**站点水印不要写进 `.jps`**：一旦写进去，用户在应用里打开也带着、复制给别人也带着，等于把"平台"
烙进"作品"；以后换域名/换活动还得批量改所有谱。

### 5.2 谱面层要显示"网站上的图片"，缺一条 URL 通道

现状（实测）：`bgImage` / `wmImage` 只认 `data:`、相对路径、`[[双链]]`；
`assetPathOf()` 不识别 `https://`；网页版没有目录句柄时 `base.kind === 'none'` 直接报错。
**所以现在做不到"站上的谱引用站上的图"**。

建议加一条通道（约 1 天，改动集中）：

1. `engine/overlayAsset.ts`：`assetPathOf()` 增加 `isUrl`（`https://` 或 `/` 开头）；
   扩展名白名单照旧（从 URL 的 pathname 取，忽略 query）。
2. `src/store/assetSource.ts`：`AssetBase` 增加 `{ kind: 'url'; base: string }`（base = `.jps` 所在 URL 的目录）；
   新增 `fetch` 读取器。
3. 读取器的硬约束：
   - 只允许 **https + 同源**（或 `meta.json` 里显式列出的白名单域）；
   - `credentials: 'omit'`、`referrerPolicy: 'no-referrer'`、超时 10s、大小上限（沿用 16MB，站点建议 2MB）；
   - 跟随重定向后**再核一次 origin**；
   - 扩展名白名单、**拒绝 SVG**（沿用现有安全口径）；
   - 读到的字节仍解码成 **data URI**（PNG/PDF 导出靠 `new Image()` 栅格化，外链会污染画布；data URI 不会）。
4. 构建期预渲染：Node 里没有 canvas，拿不到宽高。两个办法：
   - a. 在 `gen-scores.mts` 里写约 60 行的图片头解析（PNG/JPEG/WebP 的宽高），零依赖；
   - b. 作者提交前跑一次浏览器脚本，生成 `assets.json`（`{href,w,h}`）。
   推荐 a（自动、无感）。
5. 跨域：同源最省事。以后放 R2/图床必须配 CORS，否则 `fetch` 直接失败；不要用 `http:`（混合内容会被浏览器拦）。
6. 写法：`bgImage: "assets/bg.webp"`，相对这份 `.jps` 的 URL；这样站点、下载后的本地目录（谱 + assets 一起）都能用。

### 5.3 站点展示层（卡片模板）

- 谱面 SVG **只画谱**；外面的"纸面/卡片"用 HTML/CSS 包一层：底纹、圆角、阴影、页边距、角落的站点标记。
- `meta.card` 选皮肤：`paper`（纸面）/ `ink`（水墨）/ `brand`（深空蓝）/ `minimal`（极简）。
  皮肤只控制**页面与封面框**的 CSS 变量，**不控制谱面本身**（谱面只认 `.jps` 的配置）。
- 站点水印两种形态，建议默认第一种：
  - 角标：右下角小字 `https://ijipu.pages.dev/` + 谱主名（**写全协议**、可点回官网）；
  - 斜向重复：像应用里的 `wmRepeat`，但用 CSS 实现，**不进 SVG**（复制源码/下载都不带）。
- 开关：`?plain=1` 关掉所有站点装饰，方便截图/打印（也是对访客的尊重）。
- 导出图（og、首屏缩略）在**构建期**把站点水印烘焙进去；
  页面上的"下载图片"如果要做，也走预生成的静态图，而不是运行时 canvas（字体、跨域、性能都不划算）。

### 5.4 分享卡

- 分享卡 = 静态图，模板就是"配色 + 排版 + 背景图 + 水印位置"，数据从 `meta.json` 来。
- 视频的 `CardStyle` / 模板库**不复用**：它依赖 canvas、桌面专属、本机字体，网站上跑不了也不该跑。
  如果你说的"卡片模板"指的是视频里那套片头/片尾卡，它在网站上的对应物就是
  **5.3 的页面皮肤 + 这里的分享卡**，不是同一份实现。
- 生成方式：本地脚本（`npm run score:cover`）用无头 Chrome 截详情页成 `og.png`，**提交进仓库**。
  CI 只检查文件存在，不需要 Chrome。

### 5.5 安全与隐私

- 只同源、禁 SVG、限大小、`referrerpolicy=no-referrer`、不加载第三方统计图。
- `?src=` 只允许 `https:`；失败要明确说"读不到"，不静默出空谱。
- 复制源码、下载 `.jps` 是**功能**，不做"禁止右键/禁止复制"那套——挡不住，还难看。

## 八、验收与闸门

### 8.1 `npm run smoke` 新增

| 断言 | 防的是什么 |
|---|---|
| 每个 `meta.json` 字段齐全、枚举合法、无未知字段 | 手滑写错字段被静默忽略 |
| 每个 `score.jps` 解析 0 错误、0 告警（或白名单） | 发布坏谱 |
| `slug` 唯一、与目录名一致 | 链接打架 |
| `dist/scores/index.json` 与目录一一对应、排序稳定 | 列表漏谱或顺序乱跳 |

## 十、已拍板项的细说（含投诉邮箱）

### 10.1 短链就是 `/s/<短码>`（已定：做，P0）

**是**，就是分享链路里的那一个：

```
https://ijipu.pages.dev/s/7k2m   → 301 →  https://ijipu.pages.dev/scores/xiao-xing-xing/
```

- 它不是第三方短链服务，就是站内一条 301 规则（Cloudflare Pages 的 `_redirects`）。
  没有额外成本、不会过期、不怕平台把短链服务封掉。
- 为什么不直接用 `/s/小星星`：中文会被百分号编码，二维码码点变多、口播难念、平台复制还可能转义；
  4-6 位 ASCII 最稳。
- 和规范链接的关系：`/scores/<slug>/` 才是规范地址（进 sitemap、写 `<link rel="canonical">`）；
  短链只用于分发，301 会把权重带过去。
- 成本：`meta.json` 一个 `short` 字段 + 构建时生成一行 `_redirects`。现在做 ⇒ 这个字段**必填**。
- 规则：短码发布后不改；真要改就加一个新的，旧的继续 301。

**短码用自定义的，不用随机码。** 这是给"抖音/小红书里口播、字幕、二维码"用的：

- 随机码（如 `k7f2`）没人记得住、也没法念；曲库是策展制、数量可控，**撞码可以在构建时拦住**，不需要靠随机避免冲突。
- 自定义码用**拼音首字母或英文词**，3-6 位**小写字母**（不用数字，避免 `0/O`、`1/l` 混淆；也避开 2 位码，2 位太容易撞上骂人缩写）。
- 避开脏话/歧义（比如 `sb`），避开与站点路径同名的保留字（`s`、`api`、`admin`、`scores`、`app`）。
- 发布后**码跟内容绑定**：改标题、改排版都不改码；内容真的换了一首，才新开一个码。
- 以后内容多到自定义码不够用，再退回"前缀 + 2 位随机"的混合码。

起步 8 个码（**发布后不改**，改要现在说）：

| 曲目 | 短码 | 链接 |
|---|---|---|
| 小星星 | `star` | `/s/star` |
| 茉莉花 | `mlh` | `/s/mlh` |
| 欢乐颂 | `hls` | `/s/hls` |
| 两只老虎 | `lzlh` | `/s/lzlh` |
| 铃儿响叮当 | `lexdd` | `/s/lexdd` |
| 送别（完整） | `songb` | `/s/songb` |
| 送别（4 小节多声部） | `duet` | `/s/duet` |
| 友谊地久天长 | `yydj` | `/s/yydj` |

> 不用 `sb`、`dsb`、`ds`：它们在中文网络里都有骂人的联想。`xx` 也有成人含义，所以小星星用 `star`。
> 送别那条 4 小节演示是"两个声部"，用 `duet`（二重奏），干净、好念。

**怎么防重复（这是构建闸门，不靠人记）：**

1. 短码写在各自的 `meta.json` 里；构建时把所有条目（**含已下架 `retired`**）的 `short` 收成一个集合，
   发现重复就**构建失败**，报错里带上冲突的两个 slug。
2. 保留字表放在生成器里：`s`、`api`、`admin`、`scores`、`app`、`index`、`sitemap`、`robots`、`404` 等，
   不允许拿来当短码（免得和将来可能出现的路径打架）。
3. 只允许 `a-z`，长度 2-6；大小写不同也算重复（`Star` 和 `star` 都不合法，统一小写）。
4. **已下架的码不复用**：条目改成 `retired` 时目录还在、`meta.json` 还在，码继续被占着；
   如果真的删了整个目录，必须把码补进 `public/scores/_retired-short.json`（构建时一并查重）。
   为什么不能复用：旧二维码/旧链接还印在外面，复用会把它们指到另一首曲子上。
5. `_redirects` 里一条码写**两条**规则（带斜杠和不带斜杠），都是精确匹配、没有通配：
   `/s/star` 和 `/s/star/` 都 301 到 `/scores/xiao-xing-xing/`；不会出现"前缀吃掉别的码"。
6. 以后要加新码，先在表里查、再提交；撞了构建就红，不会带病发布。

### 10.2 站点水印的三种形态（已定：A 角标 + 分享卡）

这三种说的是**页面上的站点标识**，不是 `.jps` 里作者自己的水印。

| 形态 | 长什么样 | 优点 | 缺点 |
|---|---|---|---|
| **角标** | 卡片右下角一行小字：`https://ijipu.pages.dev/ · 蜗牛`（完整 URL、可点），12px、半透明 | 不挡谱、干净、专业；截图里也自然 | 只裁右下角就能去掉 |
| **斜向重复** | 整页淡水印平铺，旋转 -30°，透明度 6-10%，像应用里的「重复水印」 | 最难裁、能防"整页搬运" | 影响阅读/打印；小屏更明显；气质偏"防盗"，和分享感冲突 |
| **只在分享卡** | 页面完全干净；`og.png` 里带站点名 + 二维码 | 页面最好看 | 页面截图/打印没有任何标识 |

**已定：A。** 默认 **角标**（页面）+ **分享卡完整标识**（og 图）。
斜向重复留作 `watermark: "tile"`，将来只对个别谱开启；
任何页面都能用 `?plain=1` 关掉站点装饰，方便别人截图/打印。

实现上：都放在页面的 HTML/CSS 层，**不进 SVG**。角标是卡片里的绝对定位元素；
斜向重复用 `::before` + 一个构建期生成的小 SVG 文字瓦片（CSS 渐变只能画斜线，画不了字）。
下载的 `.jps` 和复制出来的源码都不带这些。

> 水印是"威慑"，不是"保护"。截图、拍照、手抄都拦不住；所以不做禁右键那套。

### 10.3 CC BY-NC-SA 4.0 是什么，和"保留所有权利"差在哪（已定：A）

**CC BY-NC-SA 4.0** 是知识共享许可的四个成分：

| 成分 | 含义 | 别人要做什么 |
|---|---|---|
| **BY**（署名） | 必须注明作者、来源、许可，并附链接；改过要说明 | 署名 |
| **NC**（非商业） | 不得"以商业利益或金钱报酬为主要目的"使用 | 不带货、不收费、不进商业出版物 |
| **SA**（相同方式共享） | 改编作品必须用同一许可发布 | 不能改成"保留所有权利" |
| **4.0** | 国际版，有官方中文译本；许可**不可撤回** | —— |

它**授予**公众：复制、发行、展览、表演、改编、通过网络传播（限非商业），前提是遵守 BY/NC/SA。
它**不授予**：商业使用（要另谈）、商标、专利、人格权；也**不改变原作品的权利状态**——
如果曲子还在版权期，你本来就无权许可。

几个容易误解的点：

- **不可撤回**：已经发出去的副本，别人按许可拿到的权利收不回来。你可以停止继续发布，但不能"反悔"。
- **NC 的边界是模糊的**：个人学习、非营利教学一般可以；带广告、带货、付费课程、商业出版物通常算商业。
  边界不清时，页面写一句「商用请联系」最实用。
- **SA 是"传染"的**：别人改编你的谱（改配器、改排版）也必须用同一许可，不能锁进一本"保留所有权利"的书里。
- **你仍可双重许可**：给公众 CC，同时单独给某人商业授权。
- **CC 不覆盖代码**：引擎是 AGPL-3.0，乐谱文本是另一套许可，页面上要分开写。

**和"保留所有权利，仅站内浏览"的区别：**

| 维度 | CC BY-NC-SA 4.0 | 保留所有权利 |
|---|---|---|
| 别人能下载吗 | 能 | 不能（除非你单独许可） |
| 能转发/改编吗 | 能（署名 + 非商业 + 同许可） | 不能 |
| 你事后能收紧吗 | 不能收回已发布的 | 可以（但挡不住截图） |
| 别人能商用吗 | 默认不能，需另谈 | 默认不能，需另谈 |
| 和"让更多人用 JPS"的目标 | 一致 | 冲突 |
| 对公版曲目的实际控制力 | 只覆盖你的记谱/排版 | 同样只覆盖你的部分，且更弱 |

**公版曲目的关键点**：旋律本身是公版，你能许可的只有"你的记谱、排版、编配"这部分；
别人完全可以自己重新记谱，你拦不住。所以在公版谱上写"保留所有权利"，更多是姿态，不是实质保护。

**已定：A。落地口径：**

1. 站点默认 **CC BY-NC-SA 4.0**（如果你不介意商用，将来可改用 CC BY 4.0）。
2. 页面只写：`记谱/排版：CC BY-NC-SA 4.0` + `商用请联系`。
   **不写"旋律：公版"那一行**——旋律状态记在 `meta.source` 里（如「传统民歌，作者不详」），供审计与版权页说明。
3. 原创作品让作者选，默认同一许可；不想开放的，单独标"保留所有权利"。
4. C 级片段不提供下载，标「教学引用」。
5. 代码 AGPL-3.0 单独写，别让人误以为谱也是 AGPL。

### 10.4 投诉邮箱：沿用 `snail.zh@foxmail.com` 合不合适

**结论：合适。** 它已经公开在 `src/brand/tokens.ts` 的 `authorEmail`、`package.json`、README 和关于对话框里，
再放到版权页**不会新增暴露面**；法律上也没有"必须专用邮箱"的要求，只要渠道可达、有人处理、能留证。

但有两个前提：

1. **你会长期用它**。版权页是"长期承诺"，如果这个地址两三年后不用了，投诉就断线了。
   如果可能换，最好现在就用一个会长期保留的别名。
2. **你能在 48 小时内先下架**，并且投诉邮件能归档（建一个文件夹/标签，别只靠收件箱翻）。

**已实测：`snail.zh+copyright@foxmail.com` 发不出去**（Foxmail 这个账号不支持加号别名）⇒ 不用别名。
退回"主地址 + 主题前缀 + 过滤器"：

1. 页面写 `snail.zh@foxmail.com`，并要求主题写 `【版权投诉】<作品名>`。
2. 在 Foxmail/QQ 邮箱里建过滤器：**主题包含「版权投诉」** ⇒ 移到「版权投诉」文件夹 + 标星 + 桌面通知。
3. 这个规则只在本机/账号里配，**不依赖代码**；以后换邮箱只改页面与过滤器。

- 不建议把邮箱做成图片/JS 混淆：版权方需要方便复制，混淆降低可用性，也挡不住爬虫。
- 不要放手机号。
- `pages.dev` 不能收邮件（Cloudflare 不允许在 `pages.dev` 上配 MX）⇒ 现在只能沿用已有邮箱；
  以后有自定义域名，可以用 Cloudflare Email Routing 免费做一个 `copyright@你的域名` 转发到 foxmail。
- 如果以后投诉量真的很大，再考虑专用邮箱或表单（要后端）；现在一个人维护，一个收件箱 + 过滤器更不容易漏。

`/copyright/` 页面就写这几行：

```
版权投诉：snail.zh@foxmail.com
邮件主题请写：【版权投诉】<作品名>
请附：① 作品链接（哪个页面）② 你的权利证明 ③ 你的联系方式
我们会在 48 小时内先下架，再核实。
```

> 48 小时是"先下架"的承诺，不是"处理完"；核实可能更久。做得到再写，写不到就别写具体时限。

### 关键取舍

1. **`?src=` 只带源码，不带图**：URL 取图通道是 P2；当前 8 份谱都没有附属图，够用。
2. **zip 里暂时只有 `.jps + README.txt`**：P1 没有附属图片；P2 再把 `assets/**` 收进去。
3. **`og.png` 由本地脚本生成并提交**：Cloudflare 构建镜像有没有 Chrome 没验证，不把构建押在它身上；
   新增谱要跑一次 `npm run score:og`（它会 build → 生成 → 再 build）。
4. **顶栏 6 条**是用户明确要求（2026-11-03「乐谱库链接应加到首页上面一排」）；
   旧的 adj1080「5 条」口径已同步放宽，并保留"插件手册/CLI/音色库不许回顶栏"的负对照。

# 方案：音频 → `.jps` 脚本（扒谱 / transcription）

> 产品：**爱扒谱**（英文 **iJipu BP**，仓库 / 包名 `ijipu-bp`），与 iJipu 主应用、爱出片（`ijipu-cp`）并列的第三个工具。

## 〇、先说三个"本项目独有的优势"（它们决定了这方案能做得比 noteDigger 稳）

1. **引擎能读回我们自己写的东西 ⇒ 可以自动对答案** ✓
   `parseJps()` 解析 + `checkMeasureBeats()` 逐小节时值校验 + `layoutScore()` 出排版。
   生成的谱子**过不了这三关就不许交出去** —— 这是扒谱里最贵的"自动验收"，我们天生就有。
2. **引擎能把生成的谱子放出来听，还能对着原曲听** ✓
   `buildPlaySequence()` 合成试听；`fitSync()` + `audioMsOfBeat()` 让谱子跟着原音频走。
   ⇒ 用户改一个音，立刻能 A/B 对比"像不像"。noteDigger 没有这一环（它只导出 MIDI）。
3. **"引擎是 vendor"这条路已经趟通了** ✓
   `ijipu-cp`（爱出片）已经把"新工具 = 独立仓库 + `vendor/engine` 逐字节同步 + `check:engine` 哈希闸门"跑成了标准动作
   ⇒ 新工具起步不用重新发明工程骨架。

## 一、目标与非目标

**目标（按优先级）**
1. **单声部旋律**：音频 → 音高序列 + 时值 + 调号/拍号/速度 + 小节线 ⇒ 合法 `.jps`（能被 `parseJps` 零错误解析、`checkMeasureBeats` 零告警）；
2. **可听可对**：生成后立刻合成试听；能挂原音频做 A/B（走既有 sync 口径）；
3. **可修正**：拖动改音高/位置/时值、吸附三档、撤销重做、键盘流（"错得可见、改得快"）；
4. **可交付**：导出 `.jps`；可选导出 `.jps.sync.json`（边车，让 iJipu / 爱出片拿原曲出片）、`.mid`（引擎 `eventsToMidi` 已有）。

**非目标（首版明确不做）**
- 鼓谱、歌词自动识别（歌词留空，后期手填；`C:` 行结构已支持）；
- 复音/钢琴双手全自动多声部（先做"分层辅助"，见 §7.5）；
- 自由速度（rubato）、渐快渐慢的精确还原（jps 只有全局 `J:`，见 §5.3）；
- 一次全对 —— 产品口径是"**改动数**"，不是"零错"（同 OMR 方案的口径）。

### 2.2 数据流（这条链是它最值得学的地方）

```
文件(mp3/wav/mp4…)
 └─ Web Audio decodeAudioData → AudioBuffer → Float32Array 单/双声道
     ├─ STFT：44100Hz、8192 点实数 FFT、Hanning 窗、**20 帧/秒**、分析 C1–B7（84 bins）
     │    └─ 线性谱 → 对数频率谱：先按 FFT 泄露核模拟，再在对数坐标用 Hanning 窗重采样
     │         （窗宽 ∝ 中心频率 ⇒ 低频宽、高频窄）
     ├─ CQT（Worker 后台算，可选）：每半音一个滤波器，BlackmanHarris 窗、窗长 2.8 倍周期
     │    └─ 与 STFT 融合：CQT 大处 `hypot(a,b)/√2`（突出），CQT 小处几何平均（压制）
     ├─ 归一化：能量域"每帧方差 = 1"（Welford 在线算法）
     └─ 84×N 的对数谱矩阵
         ├─ 画频谱（背景 canvas + dirty 标记，只有它重绘）
         ├─ 节奏分析：谱通量 → 峰值 → 自相关求 BPM → 动态规划节拍跟踪 → 重拍
         ├─ 调性：12 音级能量 → 取能量最大 7 个音级拼十六进制串 **查表** 得调名
         ├─ 自动填充：逐 bin 阈值起止（作者自评"效果差"）
         ├─ AI 扒谱：ONNX（onnxruntime-web）→ 后处理成音符
         └─ 音符交互：`{y: 音高bin, x1, x2: 帧, ch: 音轨, selected}` 的事件数组
```

### 2.3 关键参数（可直接抄的数值）

- FFT 8192 @44100 ⇒ 频率分辨率 5.4Hz；作者注释："最低能分辨 F#2，但足矣"。
- 帧率 20fps（50ms/帧）⇒ 120BPM 的十六分音符（125ms）刚好两帧多，够用。
- 对数频率重采样核：`cos(12·log2(f/f0)·π/0.667)+1`（偏离 0.667 半音以外取 0）。
- 调性查表：`'024579b'→C`、`'013568a'→C#'`、`'124679b'→D`…（12 条，按能量最大的 7 个音级升序拼串）。
- 节拍：`EllisBeatTrack(onsetEnv, sr, tightness=100, bpm=-110, range=[40,200], winSec=16, hopSec=1)` + `beatTrackDp(localscore, framesPerBeat, tightness=110)` 动态规划。
- 量化：精度参数 x，"用时长比 `音符时长/x` 小的、最大的 2^k 分音符"对齐首尾（x 越大越要求打点准）。
- AI 后处理：`frame_thresh=0.22 / onset_thresh=0.38 / min_note_len=6 / energy_tol=10 / midi_offset=24`；峰值后向搜索、允许断 energy_tol 帧、邻半音清零、再补漏音。

### 2.4 它自己的定位（很重要，别误解）

README 与更新记录里作者反复讲：**AI 只是"参考轨"**，官方流程是"AI 出参考 → 锁轨静音 → 人工在频谱上把剩下的扒完"。
它比专业频谱软件强的只有"体积小、双击即用"，而不是识别精度。⇒ **我们不要把宝押在 AI 上**，要把宝押在"人工修正的效率 + 生成即合法"上。

## 三、它踩过的坑 / 我们不该照抄的地方

| # | noteDigger 的做法 | 为什么我们不照抄 |
|---|---|---|
| 1 | **不保存音频数据**（省内存）⇒ 想跑 AI 得重新选文件 | 分析结果与音频必须同源可重算；我们存"降采样单声道副本 + 对数谱"，原始文件只存路径 |
| 2 | 无框架 vanilla JS，全局对象当状态 | 我们状态复杂得多（频谱/音符/小节/撤销/多文档），用 React + Zustand（同 iJipu） |
| 3 | 只有 84 bins（C1–B7） | 低音（B0–B1）与高音（C8）都要：**88 bins（A0–C8）**，代价只多 4 格 |
| 4 | MIDI 第 10 轨 = 打击乐，扒旋律要自己避开 | 我们导 jps 为主，MIDI 只是附带；真导 MIDI 时用引擎 `GmChannelAllocator` 处理通道 |
| 5 | 全局单 BPM，变速靠"每小节拖小节线" | jps 压根没有小节级变速（见 §5.3）⇒ 不能承诺"逐小节 BPM"，只能全局拟合 + 提示 |
| 6 | 撤销只记 16 步 | 至少 100 步；扒谱是高频微调，撤销深度就是可用性 |
| 7 | AI 模型是作者毕设、许可未标 | 走 **basic-pitch ONNX（Spotify，Apache-2.0）**，不碰来源不明的模型 |

## 五、jps 的硬约束（这几条决定了生成器怎么写）

这一节是全篇最要紧的地方：**扒谱工具的输出不是 MIDI，是 jps 文本**，而 jps 的表达能力比 MIDI 窄得多。

### 5.1 时值只有"2 的负幂 × 附点 + 增时线"

`docs/SYNTAX.md` 87–105 行：`1/` = 1/2 拍、`1//` = 1/4 拍、`1 -` 每条 +1 拍、`.` ×1.5、`..` ×1.75。
⇒ **可表示时值（拍）= {2^-n} × {1, 1.5, 1.75} 与 {1+k}（k 条增时线）的组合**。
⇒ **三连音写不出来**（全文档 grep 无"三连音"）。这是硬伤，必须提前告诉用户：遇到三连音曲子，工具只能"就近量化 + 标出来"。

### 5.2 跨小节的长音必须用连音线

实测 `docs/SYNTAX.md` 560 行：`(6- | 6)-` 表示"一个 6 共 4 拍"，**连音线可跨小节、跨行**，且收尾的 `-` 给合并后的长音加拍。
⇒ 生成器遇到"起点在 N 小节、跨度跨过小节线"的音，必须写成 `( x- | x )-` 形式，不能把时值硬塞进一个小节。
⇒ 这也是 **小节线必须是"硬边界"** 的原因：`checkMeasureBeats` 会逐小节核时值，塞不进就报警。

### 5.3 速度是全局的，拍号可以中途改

- `J:` 只有一个（头部）；中途只有 `&rit`（渐慢，**显示记号**，不是逐小节 BPM 表）。
- 拍号可以在**小节线备注**里临时改：`|"p:2/4"`（`measures.ts:59 inlineMeterBeats`，正则 `p\s*:\s*(\d+)\s*/\s*(\d+)`）。
⇒ 结论：**扒谱结果只能落在"全局一个 BPM"的网格上**。真遇到变速曲，只有两条路：
  (a) 取主段 BPM，把偏差大的小节标"待确认"，让用户手动拆段（产物仍是单速谱）；
  (b) 给引擎加"小节级变速记号"（如 `|"t:132"`）——**这是引擎级改动**，牵动播放、对拍、动态谱、出片四条链，必须单独立项（本次不做，见 §八）。

### 5.4 没有"竖排和弦"

同一个 `Q:` 行里，音符只能横向排；同时响的几个音只能拆成多个声部行 `Q1:` / `Q2:`（`Q1"女声":` 可带声部名）。
⇒ 钢琴/吉他柱式和弦扒出来就是"若干条独立节奏的声部行"。这直接决定 §7.5 的分层策略。

### 5.5 每小节必须凑满

`checkMeasureBeats()` 会报"第 N 小节共 X 拍，与拍号 Y/4 不符"。生成器必须保证：
`Σ(一小节内所有带时值元素) == 拍号分子`，不够的用 `0`（可见休止）或 `8`（隐藏休止）补齐。

## 六、技术路线三选一（请你裁决）

| 路线 | 做法 | 优点 | 代价/风险 | 适用 |
|---|---|---|---|---|
| **A 纯 DSP（JS 自研）** | FFT/STFT/对数谱/谱通量/自相关/DP 节拍 + HMM 音高跟踪，全在 Worker 里跑 | 零依赖、零模型、可离线、体积小（几十 KB）；noteDigger 已证明**纯 JS 够用**（作者 2025-08-12 记录：CQT 的 JS 版比 WASM 还快一倍） | 复音准确率有天花板；要自己调参 | **P0–P2 主路线** |
| **B DSP + 本地 AI** | A 打底 + basic-pitch ONNX 出"参考轨"，人工修正 | 复音/钢琴明显更准；模型与代码都是 **Apache-2.0**（可商用），官方有 ONNX 权重、体积小 | 要加 `onnxruntime-web`（需**先问你**加依赖）；CPU 推理几十秒；仍要人工修 | P3 |
| **C 现成算法库** | essentia.js / librosa-wasm | 省算法工作量 | 体积大、参数黑盒、许可与打包都要谈；与"引擎纯 TS"口径冲突 | 不建议 |

**推荐**：**A 起步（先把"能出合法 jps"打通）+ 引擎自检闭环压错 + B 在 P3 作为可选参考轨**。
理由：我们的护城河不是识别率，是"**输出即合法 + 能对着原曲听 + 改得快**"。

## 七、关键设计（五条决定"好不好用"）

### 7.1 数据模型：秒与拍两套坐标，一个源头

```ts
/** 分析出来的原始音符：只有秒，没有拍 */
interface RawNote { midi: number; startMs: number; endMs: number; velocity: number; voice: number }
/** 上了拍的音符：由 RawNote + 网格参数算出来，可回推 */
interface GridNote extends RawNote { startBeat: number; durBeats: number; bar: number; beatInBar: number }
/** 网格参数（用户可改，改一次全量重算） */
interface GridOptions { bpm: number; meter: string; firstBeatMs: number; grid: 1|2|4|8 }  // grid = 每拍切几份
```
- 编辑永远改 `RawNote`（秒）⇒ 换 BPM/换网格不会丢信息；
- `GridNote` 是**派生**，不落盘；落盘只存 `RawNote[] + GridOptions`（+ 小节线手动修正表）。

### 7.2 量化 + 时值分解（核心算法）

```
RawNote → 拍坐标（(ms - firstBeatMs) / beatMs）
 → 对齐 onset 与 dur 到 1/grid 拍网格（就近取整，保留原始偏差用于"告警"）
 → **可表示性检查**：用引擎自己的 tokenDuration 建一张"时值 → token 串"反查表
      （枚举 `1`/`1/`/`1//`/`1.`/`1..`/`1-`/`1--`… 用 tokenizeJpsMusic + tokenDuration 算真值，memoize）
 → 不能用一个 token 表达 ⇒ 拆成 2 的幂之和（贪心 + 二进制唯一分解），用连音线 `( … )` 串起来
 → 跨小节 ⇒ 在小节线处断开，`( x- | x )`（§5.2）
 → 小节内时值不足 ⇒ 补 `0`（可见休止）或 `8`（隐藏）
 → 产出 jps 文本 + **报告**（哪些音被拆过、哪些偏差 > 1/4 拍、哪些三连音没表示）
```

**为什么反查表要用引擎的 `tokenDuration` 而不是自己写规则**：语法是引擎的唯一口径，自己抄一份必然漂移（iJipu 历史上这类"两处口径"吃过亏）。用引擎算真值，语法一改生成器自动跟上，且能在 `smoke` 里逐条断言。

### 7.3 三闸门自检闭环（照搬 OMR 方案的做法）

```
生成文本 → ① parseJps 零错误 → ② checkMeasureBeats 零告警 → ③ layoutScore 不抛且行数 > 0
   ├─ 全过：进预览/试听
   └─ 任一不过：**不静默降级**。把失败小节退化成"整小节休止 + 标黄"，
                并在报告里写清原因（"第 7 小节 3.5 拍，拍号要求 4 拍"），让用户点一下就能改
```

### 7.4 人工修正是一等公民（这是产品成败处）

- **键盘流**：`↑↓` 改音高、`←→` 移位置（按当前吸附格）、`Shift+←→` 改时值、`Del` 删、`Ctrl+Z/Y` 撤销、空格试听、`T` 在小节线处打拍点；
- **吸附指示**：光标处实时显示"落在第 3 小节第 2 拍 + 1/2"，拖的时候数字跟着变（比画辅助线便宜且更准）；
- **A/B 试听**：`buildPlaySequence` 合成谱子，与原音频**同一时钟**播放（引擎 `audioMsOfBeat` 换算），一键切换"只听谱 / 只听原曲 / 一起"；
- **差异高亮**：谱子与原始 `RawNote` 不一致（被拆过、被量化挪过 > 1/4 拍）的音染一个角标，用户一眼知道哪该复核。

### 7.5 复音与多声部：分层，不硬猜

- **P2 单声部**：只出旋律（最高音线 / 能量最强的一路），`Q:` 一行；
- **P3 分层辅助**：按"音高区间"把频谱分层（低音 / 中声部 / 旋律），每层各跑一次单声部扒谱 ⇒ 生成 `Q1:`/`Q2:`/`Q3:`；
  用户可只勾选其中一层导出（默认只导旋律）；
- **和弦名**（可选）：每拍统计活跃音高集合 → 与 12×4 个和弦模板（大三/小三/属七/减三）比对 → 显示在时间条上，**只做提示，不写进 jps**（jps 的 `{bz}` 是伴奏声部记谱，不是和弦标记，见 `SYNTAX.md` 917 行）。

### 8.2 引擎侧要新增什么（进 `packages/ijipu-engine`，因为它是"纯、可测、两端共用"的那部分）

```
packages/ijipu-engine/src/engine/transcribe/
  ├─ types.ts      RawNote / GridNote / GridOptions / TranscribeReport
  ├─ grid.ts       quantizeToGrid(notes, opts) → GridNote[]        // 秒 → 拍 + 网格对齐
  ├─ tokens.ts     durationTokens(beats) → string[]（用 tokenDuration 建反查表，memoize）
  ├─ toJps.ts      transcriptionToJps(notes, opts) → { text, report }   // 唯一语法出口
  └─ anchors.ts    transcriptionToAnchors(notes, opts) → SyncAnchor[]   // 每小节一条锚点
```

**为什么放引擎而不是新仓库**：
1. 它是纯函数、零 DOM ⇒ 符合引擎纪律，且能在 `scripts/smoke.mts` 里直接断言（那里的断言已经这么干了，33k 行）；
2. "音频/MIDI → jps" 这件事**插件端也用得上**（例如以后"把 MIDI 拖进 Obsidian 生成谱面"），那时靠 `vendor/engine` 自动共享；
3. 语法口径只有一份：生成器与解析器在同一个包里，改语法时能一起改、一起测。

**明确不进引擎的东西**（理由：宿主能力 / 体积）：
FFT/CQT/Worker/AudioBuffer/画布/模型 —— 这些留在新应用的 `src/analysis` 与 `src/ui`。
（引擎要被同步到 Obsidian 插件里，几十 KB 的 DSP 塞进去只增体积、插件端又没音频可分析。）

1. **"在 iJipu 中打开"**：保存 `.jps` → 调系统默认程序（iJipu 已注册 `.jps` 文件关联，`tauri.conf.json:37 fileAssociations`）；

## 十、测试与验收（这套"合成信号 + 闭环"是本方案最省钱的部分）

1. **合成信号夹具**（不依赖任何音频素材）：
   - 正弦波旋律（每个音 1 拍 / 半拍 / 附点，含休止）⇒ 断言扒出的音符序列 == 输入；

3. **真曲回归集**（`samples/transcribe/`，自己录或用无版权素材）：每条记录"音符数 / 人工改动数 / 耗时"，作为回归指标。
4. **性能预算**（3 分钟歌，44.1kHz 立体声）：
   - STFT：20fps × 180s = 3600 帧 × 8192 FFT ≈ 3000 万点 ⇒ JS(WASM 无) 目标 **1–2 秒**（Worker）；
   - 对数谱内存：3600 × 88 × 4B ≈ **1.2MB**（很小，随时重算都行）；
   - 音频副本：降采样到 22050 单声道 ≈ **16MB**（可接受，别存 44.1k 立体声的 63MB）。

## 二十一、P0.12 —— 时点线跟着走、翻页改成"贴边就翻"、把白屏那个死循环修掉（2026-11-18）

**修掉的**（这次的收获主要在这条线上）
- **按空格白屏的真凶**：自动翻页那个 `useEffect` 的依赖里有 `view`，而它自己又调 `setView`。

- **翻页口径**：阈值从 `panMs + span * 0.82` 改成贴右边缘（`panMs + span - 1`），翻页后播放头落在

## 二十二、P0.13 —— 播放停不下来、时点线、默认数字、区间内点击、一屏 20 秒、键格（2026-11-18）

用户六条（m03712）。前两条是同一个根因，值得单独记下来。

**① 播放停不下来 / 播放按钮与空格都像"跳跃播放"**
`audio/player.ts` 里 `play()` 与 `stop()` 共用模块级的 `raf` / `onTick` / `onEnd`：
- `App.startPlay` 是 `await play(...)` **之后**才 `setPlaying(true)`。`play()` 里有
  `await ctx.resume()` / `await synth.ready()`，在这几十毫秒里用户再按一次空格，
  `playing` 还是 false ⇒ 又走"开始播放"分支，于是**两路 tick 同时存在**；
- 旧那路的 rAF id 早被后一次 `play()` 覆盖，`stop()` 的 `cancelAnimationFrame(raf)` 只取消得掉最新那路，
  旧的继续每帧回调 `onTick` ⇒ 时点被两路来回写，看起来像"跳跃播放"，也停不下来。

修法：
- `player.ts` 加 `let runId = 0`，`stop()` 与 `play()` 都 `++runId`，`play()` 在**每次 await 之后**

- `App.startPlay` 改成**先** `setPlaying(true)` 再 await，`play()` 回 false 就不再动状态。

**② 时点线不跟随** —— 其实是 ① 的连带：状态被两路写、`playing` 还会被顶回 false，
桌面壳里看起来就是"线不动"。修完之后在 headless 用合成音模式实测（时点用 `performance.now()` 推，

**③ 默认音名 → 数字**：`store.pitchMode` 默认值 `'name'` 改成 `'number'`。

## 二十七、P0.18 —— 右栏滚轮微调、键列上的锁、黑格数字的左边距（2026-11-19）

用户四条（m05454 / m05515 / m05580 / m05608）。

**改了什么**
- **右栏滑条可以用滚轮调**，而且不会带着右栏一起滚：
  在 `.side` 上挂原生 `wheel`（`{ passive: false }`）——React 的 `onWheel` 是 passive，`preventDefault` 拦不住滚动。
  只认鼠标下面那条 `input[type=range]`，按 `step`（按住 Shift 翻 5 倍）加减，再夹到 `min/max`。
  改值必须走原生 setter + 派发 `input` 事件，直接写 `el.value` 会被 React 的 value tracker 当成"没变"。
- **键列右上角加了一把锁**（在"1=bB"调号右边，锁上时琥珀色、开锁时灰蓝），点击切换：

  probe 里"拖播放区间 / 点时间尺挪播放头"三条立刻变红，加上右边界才对。
- **黑格里的数字音符左边距跟白格对齐**：白格写字在 `x = 5`，黑格改成 `KEY_BLACK_X + 5`（同样从块左缘留 5px），

## 二十八、P0.19 —— 选择模式下按住 Alt 临时当绘制（2026-11-19）

## 二十九、P0.20 —— 改音高（拖 + 方向键）、50 步撤销、右缘光标（2026-11-19）

用户 m05736（"两种方式都要"＋"添加，50 步撤销"）与 m05780（音符右缘要变左右箭头）。

**改音高的两条路**
- **上下拖音符**：`Drag` 的 `move` 多记 `grabY` 与按下时的 `midi`，移动时按
  `dRow = round((grabY - y) / ROW_H)` 平移半音（往上拖 = 升 key），和时间平移一起生效 ——
  一次拖动可以同时改"什么时候响"和"响哪个音"。
- **方向键**：选中音符后 `↑/↓` ±1 半音，`Shift+↑/↓` ±12（一个八度）。走 `patchNote`，
  自动压撤销栈，所以按错了 Ctrl+Z 就回来。

**50 步撤销**
- 状态里加 `history: RawNote[][]`，每个改谱动作（加/改/删/确认/全选/回到初稿）之前压一份
  **整份 notes 快照**。为什么不存 diff：音符量级几百到几千，快照便宜；diff 反而容易出
  "撤销后跟原来差一点"的坑。
- **一次拖动算一步**：`NoteRoll` 在 `pointerdown` 调 `beginEdit()`、`pointerup` 调 `endEdit()`，
  中间几十次 `patchNote` 只在第一次真正压栈（`gestureDepth > 0 && gestureSaved` 直接返回）。
- 上限 50 步（超了从最老的丢）；换文件（`setLoaded`）时清空。
- 入口：`Ctrl+Z`，以及工具条上新增的「撤销」按钮（没有历史时是灰的）。

**右缘光标**
- 绘制模式（或按住 Alt）下，鼠标停在某个音符右缘 8px 内，光标变 `ew-resize` ——
  让人看得出这里能拉时值；区间握柄本来就是这个光标，不冲突。

**验证**：typecheck 通过；smoke **59/59**（新增 3 条：一次拖动只算一步、再撤一步回到加音前、
撤销栈最多 50 步）；`npm run probe` **66/66**（新增 6 条：右缘 `ew-resize`、上下拖 64→66、
`↑` 67、`Ctrl+Z` 回 66、撤销按钮 3→2、无历史时按钮灰）；`tauri:build --no-bundle` 通过。

**没验的 / 已知限制**：只做了撤销、没做重做（redo）；撤销不含"播放头/视野/模式"这些界面状态，
只回退音符表。
